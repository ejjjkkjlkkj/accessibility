# Architecture contract: independent language tracks and universal language

## Non-negotiable rule

Every programming language in the shared catalogue has its **own independent implementation track**. The tracks must not be merged into one generic implementation merely because their role IDs or event contracts are compatible.

For each language `<id>`, maintain three separately versioned deliverables:

1. **Screen reader** — `screenreader/<id>`: accessible-tree ingestion, semantic navigation, keyboard commands, focus/state handling, speech and braille interfaces, error handling, tests and packaging.
2. **UEFI / bare metal** — `uefi/<id>`: firmware entry point, boot services/runtime boundary, console/input interfaces available on the target, bounded memory use, build artifact and simulator/hardware evidence. This is a distinct target, not a flag on the hosted build.
3. **Operating-system integration** — `os/<id>`: native OS adapter(s), event subscription, accessibility tree/actions, keyboard/focus behavior, speech/braille routing and target-specific tests.

These are **logical track IDs and required deliverables**, not a claim that every directory or implementation already exists. Existing source files may live in the current language-specific directories until migration is deliberate and tested. Each track has its own status and release gate.

## Language isolation

- Each implementation must compile and test with its own declared toolchain and target constraints.
- A language may consume the documented stable ABI or canonical JSON contract, but must not silently depend on another language's runtime or executable.
- Shared role numbers and schemas define interoperability only; they do not make binary layouts, calling conventions, runtime behavior or OS adapters interchangeable.
- Language-specific implementations must not be generated by renaming one source file and claiming completion.
- For every language, record compiler/runtime version, target, dependencies, license, build command, tests, artifact hash and known gaps.
- A language/target that cannot safely support a requirement must be labelled `BLOCKED` or `NOT_APPLICABLE_WITH_REASON`, not marked PASS.
- Hosted screen-reader, UEFI and OS statuses are independent. One green gate cannot promote the other two.

## Initial language scope

The catalogue in `projects/manifest.json` is authoritative for the languages to track. The currently active native-core set includes C, Rust, Go, D, Ada, Zig, Nim and Swift. Other catalogue entries—including C++, assembly targets, Python, Java, JavaScript/TypeScript, Scratch and U—remain separate tracks with honest capability and toolchain assessments. Scratch is an educational/prototyping track, not a claim of production UEFI capability. U must be tied to a precisely identified compiler/toolchain before any capability claim.

## Universal language: NEXORA

NEXORA is a **separate experimental universal language**, not a replacement for the individual language implementations and not a synonym for the shared accessibility contract.

Its responsibilities are:
- define a stable, versioned, language-neutral semantic IR for accessible nodes, states, events, navigation commands and errors;
- define deterministic parsing, validation, type rules and bounded execution;
- provide explicit backend/FFI boundaries for each supported host language, OS and firmware target;
- allow per-language model adapters to translate to/from the canonical representation without erasing language-specific semantics;
- keep AI optional for core navigation, with no direct privileged actions from model output.

NEXORA does **not** become a universal compiler, universal runtime, native OS adapter or UEFI screen reader merely because its grammar, IR or reference interpreter exists. Each backend, adapter, target and release must pass its own tests.

## Required status fields and release gates

For every language, track these separately:
- `screenreader_status`
- `uefi_status`
- `os_status`
- `toolchain_status`
- `release_status`

Allowed evidence labels: `PASS`, `FAIL`, `PARTIAL`, `BLOCKED`, `NOT_VALIDATED`.

A PASS requires reproducible logs and artifacts for that exact language/target. QEMU/emulator success must be labelled simulation; it is not proof of physical hardware behavior. No CI job may flash firmware, write NVRAM, or reboot physical hardware.

## Immediate implementation sequence

1. Preserve and test the current eight-language native core independently.
2. Add per-language build/test/release manifests rather than treating a shared role contract as implementation.
3. Build each language's hosted screen reader, UEFI artifact and OS adapter as three distinct deliverables.
4. Extend the same separation to every other catalogue language, using target-appropriate scope and honest BLOCKED reasons where needed.
5. Implement NEXORA's language/IR/compiler backends as a separate track and add conformance tests between it and each language adapter.
6. Release only the tracks whose own gates pass; never infer a full screen reader from a role enum, data structure, stub, mock or successful compile alone.
